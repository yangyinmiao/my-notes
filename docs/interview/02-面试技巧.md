# 面试技巧

## 1. 自我介绍

自我介绍是面试的第一流程，也是你给面试官的第一印象。不要讲流水账，不要把简历逐条复述。面试官关注的核心是：你和岗位的匹配度。

建议时长控制在 1 到 2 分钟，避免空话和废话，在有限时间内灌输重点。

不要重点讲籍贯、爱好，也不要泛泛地说“我很努力、很认真”。

参考模板：

1. 亮身份（学校/公司）+ 核心标签
	例如：我叫 xx，做过 5 年 AI 开发，擅长 Agent、RAG 系统，熟悉常见 AI 应用框架，对模型训练与推理有实践经验。
2. 用结果证明能力
	例如：通过 xx 方法实现 xx 提升。使用我搭建的 RAG 系统，相比通用方案，回答时延降低 xx%，准确率提升 xx%。
3. 体现诚意与匹配
	例如：我研究过贵公司项目形态，认为我的技术栈与岗位匹配，也认同团队技术方向，期待加入并承担实际业务目标。

## 2. 反问

### 核心逻辑

这个环节主要用于判断：

- 你是否真的想来，而不是随便看看
- 你的关注点是什么、关注深度如何
- 你是否对岗位有深入思考

### 参考问题方向

针对不同面试官，问题要有差异：

1. 业务主管（通常一面，未来可能是直接同事）
	可问：
	- 团队人员结构与能力分布（大团队/小团队、协作方式）
	- 上下游关系与话语权（哪个团队主导关键决策）
	- 对候选人的预期（入职后 3 个月/6 个月要完成什么）

2. 大老板（通常是 +1/+2，技术终面或业务终面）
	可问：
	- 公司战略与业务线规划
	- 当前业务是增量探索还是存量优化
	- 未来 1 到 2 年持续投入方向与资源安排

3. HR
	可问：
	- 职级晋升通道与节奏
	- 培训机制与成长支持
	- 团队制度与协作文化

说明：薪资、社保、公积金等细节更适合在进入意向沟通阶段再展开细聊。

## 3. 简历编写技巧

（本节部分观点参考《大模型工程师面试》并结合实践经验整理）

### 3.1 简历设计原则

大模型工程师简历中的项目描述建议遵循“背景-目标-过程-结果”四段式：

- 背景：项目所属业务场景、核心需求与约束。
  例如：面向医疗文档问答场景，服务某机构客服平台。
- 目标：明确技术目标或改进方向，如准确率提升、时延下降、成本优化。
  例如：通过微调提升术语识别准确性并满足私有化部署要求。
- 过程：突出关键技术方案和工程实现细节，明确你负责的部分。
  例如：负责样本构建与指令模板设计，采用 LoRA 微调，并用 FastAPI 封装推理服务。
- 结果：必须量化。
  例如：模型准确率提升 15%，平均响应时延降低到 600ms。

该结构能帮助面试官快速定位你的职责边界、技术能力和项目价值。

### 3.2 技术标签的提炼与对齐

简历项目应显式体现与岗位匹配度高的技术要素。大模型方向建议覆盖以下维度：

1. 模型层面
	Transformer、BERT、GPT、GLM、Qwen、Baichuan、ChatGLM 等。
2. 训练与调优
	LoRA、QLoRA、RLHF、SFT、Prefix Tuning、Loss 设计等。
3. 推理部署
	LLM 服务化、Triton、ONNX、INT8 量化、TensorRT、FastAPI、Docker、K8s 等。
4. 系统组件
	LangChain、RAG、向量检索、插件调用、多 Agent 协同等。
5. 数据处理
	分词、Token 控制、数据增强、Prompt 构造、语料清洗、HNSW 索引等。
6. 工程工具
	PyTorch、Transformers、Weights & Biases、MLflow、Redis、MongoDB 等。

这些关键词既可融入项目描述，也可在“技术栈”单独列出，以便 ATS 和招聘者快速识别。

### 3.3 亮点挖掘与差异化展示技巧

面试官更关注你在项目中“主导了什么、独到点是什么、是否体现技术判断”。

建议重点展示：

1. 决策过程
	解释为何选择某方案、对比过哪些替代方案，以及最终技术判断依据。
	例如：为何选择 LoRA 而非全参微调，或为何暂不采用多模态方案。
2. 问题解决能力
	说明技术难点与解决路径。
	例如：推理稳定性不足时如何做策略优化提升鲁棒性。
3. 可复用性与通用性
	若成果可复用到团队其他业务，要明确强调。
4. 结果与影响力
	用量化指标体现价值。
	例如：上线后日处理请求约 10 万条，平均准确率 92.3%。

### 3.4 常见误区与改进建议

常见误区：

1. 描述大而空
	例如“负责大模型微调”“参与多模态部署”这类泛化表达。
2. 工具堆砌
	只列工具名，不解释实际作用与业务价值。
3. 缺少结果
	无明确指标，导致价值无法评估。
4. 逻辑混乱
	过程过长但缺主线，面试官难抓重点。

改进建议：

- 多用“设计/主导/实现/优化”等主动动词，少用“参与/协助”。
- 按“背景 -> 问题 -> 技术方案 -> 结果”组织叙述。
- 明确区分个人贡献与团队成果。

## 4. 面试准备建议

### 4.1 刷题、论文，还是项目经验？

大模型岗位竞争激烈，候选人常面临关键选择：

- 强化算法刷题
- 深耕论文理解
- 构建高质量项目经验

三者作用不同、适配岗位也不同。应从岗位匹配、能力增长路径、面试实战收益三个维度做平衡。

#### 4.1.1 刷题

算法题（如 LeetCode/LintCode/牛客高频题）主要考察：

1. 基础数据结构与算法
	数组、链表、哈希、堆、栈、队列、树、图等。
2. 算法思维训练
	动态规划、二分、回溯剪枝、贪心等。
3. 代码实现能力
	语言熟练度、边界控制、复杂度评估。

在大模型岗位中，刷题不是唯一核心，但具有以下价值：

1. 校招/初级算法岗位的基础门槛。
2. 体现逻辑思维与编码效率，适配多轮结构化面试。
3. 补齐工程实现中的基础能力（矩阵运算、图结构、窗口优化等）。

建议每天保持 30 到 60 分钟训练，稳住下限能力。

#### 4.1.2 论文

阅读并复述经典大模型论文，是建立理论框架与技术解释力的关键路径。

常见高价值场景：

1. 算法岗、研究岗、高级工程岗面试。
2. 原理问答或开放式问题。
3. 从简历项目延展追问“为何有效、为何选该策略”。

建议分层构建论文知识体系：

1. 第一层：主流架构论文（Transformer、GPT、BERT、T5）。
2. 第二层：微调与训练策略（LoRA/Adapter、Scaling Law、RLHF）。
3. 第三层：工程相关论文（RAG、Agent、Prompt 优化、多模态处理）。

论文学习重点不是死记细节，而是形成“结构-机制-适用边界”的解释能力。建议每周精读 1 到 2 篇并输出结构化笔记。

#### 4.1.3 项目

在大模型岗位评估中，项目经验通常权重最高，因为它直接体现“解决真实问题”的能力。

优势主要在于：

1. 真实场景还原
	覆盖模型构建、训练调试、接口封装、系统部署、性能评估全流程。
2. 协作能力呈现
	体现跨团队对接、问题推进与协同落地能力。
3. 创新与优化价值
	非标准问题处理、新技术组件引入、本地化部署实践，均是加分亮点。

项目准备策略：

1. 选 1 到 2 个重点项目深挖，少而精。
2. 准备项目结构图，帮助面试官快速理解任务边界。
3. 围绕“问题-方案-结果”形成可复述的技术故事线。
4. 如有条件，提供代码仓库或在线演示，提高可信度与可展示性。

### 三者组合建议

| 岗位类型 | 推荐优先级 | 理想组合方式 |
| --- | --- | --- |
| 校招/初级算法岗 | 刷题 > 项目 > 论文 | 高频题 + 1 到 2 个基础项目 + 通用模型论文理解 |
| 微调/数据工程岗 | 项目 > 论文 > 刷题 | 数据管线实践 + 微调流程 + LoRA 论文阅读 |
| 推理部署工程岗 | 项目 > 刷题 > 论文 | 服务封装经验 + 推理延迟优化 + 部署框架掌握 |
| 高级算法/研究岗 | 论文 > 项目 > 刷题 | 论文主导答题 + 系统级项目经验 + 基础刷题稳定 |
| Agent/RAG 方向开发岗 | 项目 > 论文 > 刷题 | LangChain 项目实践 + RAG 结构论文 + 优化讲解 |

最终目标是构建三维能力体系：

- 基础能力稳定（刷题）
- 理论支撑扎实（论文）
- 工程实践落地（项目）

三者并非对立，而是候选人综合能力呈现的三大支柱。应根据岗位类型和个人阶段匹配主线方向，并形成协同优势。

## 5. 两周打卡清单（Agent/RAG 岗）

使用方式：每天按顺序完成，完成后打勾。每晚用 10 分钟做复盘，确保第二天能延续推进。

### Day 1

- [ ] 项目：确定题目与范围（Agentic RAG），完成技术选型（LLM、向量库、框架、部署方式）
- [ ] 项目：初始化仓库与目录结构，跑通最小 Demo
- [ ] 论文：精读 1 篇 RAG 基础论文并写 1 页笔记
- [ ] 刷题：哈希/双指针 2 题（限时）
- [ ] 产出：项目方案文档 + 环境可运行截图

### Day 2

- [ ] 项目：实现文档导入、清洗、分块
- [ ] 项目：沉淀分块参数（chunk size/overlap）并记录理由
- [ ] 论文：精读 ReAct 并做 3 分钟口述
- [ ] 刷题：字符串/栈 2 题
- [ ] 产出：数据处理模块 + 参数记录

### Day 3

- [ ] 项目：接入向量检索并完成 TopK 召回
- [ ] 项目：做 10 条测试 query，记录召回质量
- [ ] 论文：精读 DPR 或检索经典论文
- [ ] 刷题：二分/数组 2 题
- [ ] 产出：检索接口 + 初版测试记录

### Day 4

- [ ] 项目：实现混合检索（BM25 + 向量）
- [ ] 项目：对比“仅向量 vs 混合检索”效果
- [ ] 论文：精读 Self-RAG
- [ ] 刷题：滑动窗口 2 题
- [ ] 产出：检索对比表（至少 20 条样本）

### Day 5

- [ ] 项目：接入 reranker，返回引用片段
- [ ] 项目：实现答案附来源（source/citation）
- [ ] 论文：阅读重排相关材料（如 ColBERT）
- [ ] 刷题：堆/TopK 2 题
- [ ] 产出：可追溯回答链路

### Day 6

- [ ] 项目：接入 Agent 工具（至少 2 个）
- [ ] 项目：实现工具路由策略（何时调用检索/工具）
- [ ] 论文：Toolformer 或 Function Calling 相关文章
- [ ] 刷题：BFS/DFS 2 题
- [ ] 产出：Agent 工具调用 Demo

### Day 7

- [ ] 项目：第一轮联调，修复核心 bug
- [ ] 项目：跑一轮小评测（至少 30 问）
- [ ] 论文：本周 3 篇论文串讲复盘
- [ ] 刷题：周测 3 题（限时）
- [ ] 产出：周报 1（指标、问题、下周计划）

### Day 8

- [ ] 项目：实现 Query Rewrite 或 Multi Query
- [ ] 项目：对比改造前后召回质量
- [ ] 论文：CRAG 或检索纠错相关论文
- [ ] 刷题：链表 2 题
- [ ] 产出：查询改写模块 + 效果数据

### Day 9

- [ ] 项目：做上下文压缩与 Token 控制
- [ ] 项目：优化提示词模板，减少冗余上下文
- [ ] 论文：长上下文处理相关文章
- [ ] 刷题：树题 2 题
- [ ] 产出：延迟/成本优化记录

### Day 10

- [ ] 项目：完善容错机制（重试、回退、空检索兜底）
- [ ] 项目：构建失败 case 集并逐一修复
- [ ] 论文：Agent 系统设计实践文章 1 篇
- [ ] 刷题：动态规划入门 2 题
- [ ] 产出：稳定性改进清单

### Day 11

- [ ] 项目：构建 50 问评测集（覆盖常见场景）
- [ ] 项目：实现自动评测脚本（正确性/引用覆盖/延迟）
- [ ] 论文：论文口述训练 1（抽 2 篇）
- [ ] 刷题：图题 2 题
- [ ] 产出：可复现评测报告 v1

### Day 12

- [ ] 项目：增加可观测性（日志、时延分布、命中率）
- [ ] 项目：定位 2 到 3 个性能瓶颈并优化
- [ ] 论文：论文口述训练 2（抽 2 篇）
- [ ] 刷题：综合题 2 题
- [ ] 产出：性能分析报告

### Day 13

- [ ] 项目：整理 README、架构图、运行步骤
- [ ] 项目：提炼 3 个亮点与 2 个踩坑复盘
- [ ] 论文：6 篇论文全链路串讲
- [ ] 刷题：模拟面试编码 3 题
- [ ] 产出：面试展示版项目包

### Day 14

- [ ] 项目：全流程模拟面试（项目讲解 + 系统设计问答）
- [ ] 论文：随机抽题口述（5 分钟/题）
- [ ] 刷题：限时 2 题，强调边界与复杂度表达
- [ ] 复盘：补齐短板，形成最终答题模板
- [ ] 产出：周报 2（终版结果 + 面试讲稿）

### 每晚复盘模板（10 分钟）

- [ ] 今天完成了什么？（列 3 条）
- [ ] 今天卡住了什么？（列 1 到 2 条）
- [ ] 明天最重要的 3 件事是什么？
- [ ] 当前风险：进度/理解/实现/表达（圈出最高风险项）

### 两周验收标准

- [ ] 项目可端到端运行，具备可演示链路
- [ ] 完成 50 问评测，至少有 1 版量化指标报告
- [ ] 完成 6 篇论文结构化笔记，支持口述
- [ ] 完成 28 到 35 题刷题，并完成错题复盘
- [ ] 准备 1 份 5 分钟项目讲稿 + 1 份 1 分钟自我介绍
