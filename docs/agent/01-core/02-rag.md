# RAG 技术

> 目标：理解 RAG 的完整链路、核心组件、以及如何提升检索效果。

---

## 一、为什么需要 RAG？

| 问题 | 说明 |
|------|------|
| **知识截止** | 模型训练数据有截止日期，无法回答最新信息 |
| **幻觉** | 模型对不确定的知识会"编"答案 |
| **私有知识** | 企业内部文档、个人笔记模型根本没见过 |
| **上下文窗口有限** | 不能把所有文档都塞进 Prompt |

**RAG 的思路**：用的时候再检索，而不是把知识烧进模型权重。

---

## 二、完整链路

### 构建阶段（离线，一次性）

```
原始文档（PDF / Word / 网页）
  ↓ 解析
纯文本
  ↓ 切片（Chunking）
多个文本块（Chunks）
  ↓ Embedding 模型向量化
向量
  ↓ 存入
向量数据库（Chroma / Qdrant / Weaviate）
```

### 检索阶段（在线，每次请求）

```
用户提问
  ↓ Embedding 向量化
查询向量
  ↓ 相似度搜索（cosine / dot product）
Top-K 相关文本块
  ↓ 拼入 Prompt
[系统提示] + [检索到的上下文] + [用户问题]
  ↓ LLM 生成
最终回答
```

## 三、切片策略对比

切片是 RAG 效果的关键，切不好会导致信息碎片化或语义断裂。

| 策略 | 做法 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **固定长度** | 按字符数/Token 数切 | 简单快速 | 可能截断语义 | 日志、结构均匀的文本 |
| **语义切分** | 按句子相似度边界切 | 语义完整 | 计算成本高 | 问答系统、知识库 |
| **递归切分** | 按段落→句子→词逐级切 | 保留层次结构 | 实现复杂 | 技术文档、代码 |
| **滑动窗口** | 相邻块有重叠部分 | 减少边界信息丢失 | 存储冗余 | 长文档、法律合同 |
| **Small-to-Big** | 检索小块，返回父块 | 精准召回 + 完整上下文 | 需构建父子关系 | 需要兼顾精准和完整的场景 |

**实践建议**：先用固定长度快速验证，效果不好再换语义切分。

## 四、向量数据库选型

| 数据库 | 特点 | 适用场景 |
|--------|------|---------|
| **Chroma** | 轻量、本地可用、Python 友好 | 个人项目、原型验证 ✅ |
| **Qdrant** | 高性能、支持过滤、Rust 实现 | 生产环境 |
| **Weaviate** | 支持混合检索、GraphQL 接口 | 复杂查询场景 |
| **Pinecone** | 全托管 SaaS | 不想运维 |
| **pgvector** | PostgreSQL 插件 | 已有 PG、不想引入新组件 |

## 五、提升检索效果的技巧

### 5.1 混合检索（Hybrid Search）

```
向量检索（语义）+ 关键词检索（BM25）
         ↓ RRF 融合排序
         最终 Top-K
```

向量检索召回语义相近的，关键词检索召回精确匹配的，两者互补。

### 5.2 重排序（Rerank）

```
向量检索召回 Top-50
  ↓ Cross-Encoder 重排序（更精确但更慢）
最终 Top-5 送入 LLM
```

常用模型：`bge-reranker-v2-m3`（中文效果好）

### 5.3 查询改写

用户的问题往往不适合直接做向量检索：
- **HyDE**：先让 LLM 生成一个"假设答案"，用假设答案的向量去检索
- **多查询**：从不同角度改写原问题，多路检索后合并去重

### 5.4 上下文压缩

检索到的文本块可能包含大量无关内容，用 LLM 先提取相关句子再送入最终 Prompt。

## 六、RAG vs 微调

| | RAG | 微调 |
|--|-----|------|
| **知识更新** | 实时更新向量库即可 | 需要重新训练 |
| **可解释性** | 可以展示来源文档 | 黑盒 |
| **成本** | 低 | 高 |
| **适合场景** | 知识检索、问答 | 改变模型风格/行为 |

> 两者不互斥，可以结合：先微调让模型理解领域术语，再用 RAG 提供最新知识。
